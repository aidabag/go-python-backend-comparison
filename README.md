## Описание проекта

Репозиторий содержит исходный код и инструментарий экспериментального исследования, проведённого в рамках ВКР. Цель работы — объективное многокритериальное сравнение языков **Go** и **Python** в контексте backend-разработки веб-приложений.

Практическая часть реализована в виде двух **функционально идентичных** REST API-сервисов для системы управления интернет-магазином. Оба сервиса развёртываются в Docker-контейнерах с одинаковыми ресурсными ограничениями и тестируются едиными сценариями нагрузочного тестирования посредством **Grafana k6**.

## Технологический стек

| Компонент | Go-сервис | Python-сервис |
|---|---|---|
| HTTP-сервер | `net/http` (stdlib) | Starlette + Uvicorn (ASGI) |
| Драйвер БД | `lib/pq` + `database/sql` | `asyncpg` |
| Модель конкурентности | Горутины (M:N планировщик) | asyncio + многопроцессные воркеры |
| Метрики | `prometheus/client_golang` | `prometheus-client` |
| СУБД | PostgreSQL 15 | PostgreSQL 15 |
| Контейнеризация | Docker (multi-stage build) | Docker (multi-stage build) |

Оба сервиса **не используют ORM** — взаимодействие с базой данных осуществляется через параметризованные SQL-запросы напрямую. Это обеспечивает сопоставимость эксперимента на уровне языков и рантаймов, а не фреймворков.

## Предметная область и API

Оба сервиса реализуют REST API системы управления интернет-магазином. Реализовано 17 эндпоинтов:

| Группа | Метод | Эндпоинт | Описание |
|---|---|---|---|
| Товары | GET | `/products` | Список товаров с пагинацией |
| | GET | `/products/{id}` | Карточка товара |
| | POST | `/products` | Создание товара |
| | PUT | `/products/{id}` | Полное обновление товара |
| | PATCH | `/products/{id}` | Частичное обновление товара |
| | DELETE | `/products/{id}` | Удаление товара |
| Заказы | GET | `/orders` | Список заказов |
| | POST | `/orders` | Создание заказа (транзакция с блокировкой остатков) |
| | GET | `/orders/{id}` | Данные заказа |
| Позиции заказов | POST | `/orders/{id}/items` | Добавление товара в заказ |
| | DELETE | `/orders/{id}/items/{product_id}` | Удаление позиции из заказа |
| Агрегация | GET | `/orders/{id}/total` | Итоговая сумма заказа |
| | GET | `/orders/{id}/summary` | Сводка по заказу |
| Аналитика | GET | `/analytics/orders/average` | Средний чек |
| | GET | `/analytics/products/top` | Топ товаров по продажам |
| Служебные | GET | `/health` | Health check |
| | GET | `/metrics` | Метрики Prometheus |

### Схема базы данных

```sql
products    (id, name, price, stock)
orders      (id, status, created_at)
order_items (order_id, product_id, quantity, price_at_order)
```

При создании заказа применяется **пессимистичная блокировка** (`SELECT ... FOR UPDATE`) и механизм повторных попыток при ошибках сериализации PostgreSQL (код `40001`) и дедлоках — реализован в обеих реализациях с экспоненциальной задержкой.

## Экспериментальная среда

Нагрузочное тестирование проводилось по **распределённой клиент-серверной схеме**:

| Компонент | Характеристика |
|---|---|
| Серверная платформа | VPS (Ubuntu 24.04 LTS 64-bit) |
| Процессор | 4 vCPU (AMD) |
| Оперативная память | 8 ГБ |
| Диск | 40 ГБ, Универсальный v2 SSD, 11 000 IOPS |
| Backend-сервисы | Docker-контейнеры на VPS |
| База данных | PostgreSQL 15 в отдельном контейнере |
| Генератор нагрузки | Grafana k6 на локальной машине исследователя |
| Автоматизация | PowerShell-скрипты |
| Анализ результатов | Python (numpy, scipy, matplotlib) |

Ресурсные ограничения каждого сервиса задаются через `docker-compose.yml`:
- **CPU:** 4 ядра (`APP_CPUS=4.0`)
- **RAM:** 3 ГБ
- **Пул соединений к БД:** 20 (`DB_POOL_MAX_CONN=20`)

Для Python-сервиса количество Uvicorn-воркеров задаётся переменной `WORKERS` (по умолчанию 4, соответствует числу ядер).

## Тестовые сценарии

Реализовано **5 нагрузочных профилей** (T1–T5) и **5 бизнес-сценариев** (S1–S5):

### Бизнес-сценарии

| Сценарий | Тип нагрузки | Основные эндпоинты |
|---|---|---|
| S1 Browsing | Read-heavy | `GET /products`, `GET /products/{id}` |
| S2 Orders | Write-heavy | `POST /orders`, `GET /orders/{id}/summary` |
| S3 Admin | Concurrent UPDATE | `PATCH /products/{id}` |
| S4 Analytics | Analytics | `GET /analytics/products/top`, `GET /analytics/orders/average` |
| S5 Mixed | Mixed | Все эндпоинты |

### Нагрузочные профили k6

| Профиль | Макс. VU | Длительность | Характер |
|---|---|---|---|
| T1 Load | 200 | ~4 мин | Стабильная нагрузка (все сценарии параллельно) |
| T2 Stress | 2000 | ~8 мин | Ступенчатый рост 500→1000→1500→2000 VU |
| T3 Spike | 1000 | ~5 мин | Два резких всплеска 50→1000→50 VU |
| T4 Scale | 50/100/200 | ~4.5 мин | Вертикальное масштабирование (1/2/4 CPU) |
| T5 Mixed | 200 | ~4 мин | Production-трафик: 70% чтение, 20% запись, 10% аналитика |

Перед каждым прогоном среда полностью пересоздаётся командой `docker-compose down -v`, что исключает влияние кэша и накопленного состояния БД. Каждый сценарий выполнялся **3 раза**, итоговые метрики усреднялись.

Для оценки статистической значимости различий применялся **U-критерий Манна–Уитни** (α = 0.05).

## Запуск проекта

### Предварительные требования

- Docker и Docker Compose
- Grafana k6 — инструмент нагрузочного тестирования
- Python 3.10+ с библиотеками `numpy`, `scipy`, `matplotlib`
- PowerShell (для запуска скриптов автоматизации)

### 1. Запуск стека

```bash
# Только Go-стек (сервис + его БД postgres_go, порт 8080)
docker-compose up -d golang-service

# Только Python-стек (сервис + его БД postgres_python, порт 8080)
docker-compose up -d python-service
```

> Оба сервиса слушают порт **8080**, поэтому запускаются поочерёдно.

### 2. Проверка работоспособности

```bash
curl http://localhost:8080/health
# Ожидаемый ответ: {"status":"ok"}

curl http://localhost:8080/metrics
# Prometheus-метрики в формате text/plain
```

### 3. Функциональное smoke-тестирование

Скрипты автоматически поднимают нужный стек, ждут готовности сервиса и проверяют полный цикл работы API: создание товаров и заказов, проверку складских остатков, аналитику, обновление и удаление.

```powershell
# Go-сервис
.\test_golang.ps1

# Python-сервис
.\test_python.ps1
```

### 4. Нагрузочное тестирование

```powershell
# Запуск всех профилей нагрузки последовательно для обоих сервисов
.\benchmarks\run_all.ps1
```

Результаты каждого прогона сохраняются в JSON-файлы в директории `benchmarks/results/`.

### 5. Анализ результатов

```bash
python benchmarks/analyze.py
```

Скрипт читает JSON-результаты k6, вычисляет описательную статистику, применяет U-критерий Манна–Уитни и генерирует графики в `benchmarks/results/charts/`.

### 6. Остановка и очистка

```bash
docker-compose down -v
```

Флаг `-v` удаляет тома данных PostgreSQL — необходимо для чистого начального состояния перед следующим прогоном.

**Ключевые наблюдения:**

- При стабильной нагрузке (T1, T5) разрыв в пропускной способности составляет **4–14%** в пользу Go, однако различия в задержках значительно выше — от **1.2× до 11.8×** по p95.
- При экстремальных нагрузках (T2, T3) Go опережает Python по RPS в **1.8–2.6 раза**, по числу ошибок — в **1.9–6.3 раза**.
- Go демонстрирует практически **линейное масштабирование** при добавлении CPU (4.01× при 4 ядрах), Python — менее предсказуемое (3.54×) с нарастающей задержкой.
- В аналитических запросах различия минимальны (1.2× по p95), так как узким местом становится СУБД, а не рантайм.
- В условиях production-трафика (T5) оба сервиса обработали все запросы **без ошибок** (error rate = 0.00%).

## Воспроизводимость эксперимента

Для обеспечения корректности сравнения в работе реализованы следующие меры:

- **Единый SQL-скрипт миграции** `001_schema.sql` — идентичная схема, ограничения, индексы для обоих стеков
- **Общий seed-скрипт** `002_seed.sql` — детерминированное начальное состояние (500 товаров, 250 заказов)
- **Одинаковые ресурсные лимиты** через `docker-compose.yml` (переменная `APP_CPUS`)
- **Пересоздание среды** перед каждым прогоном (`docker-compose down -v`)
- **Фиксированный порядок запуска**: сначала все прогоны Python, затем Go; между сменой стека — пауза для стабилизации ресурсов
- **Отказ от ORM** в обоих сервисах — прямые SQL-запросы через нативные драйверы
- **Идентичная бизнес-логика**: пессимистичная блокировка, retry-механизм, одинаковые форматы JSON-ответов
